## Abstract

The ancient Pyu cities of Halin, Beikthano, and Sri Ksetra were inscribed as Myanmar's first UNESCO World Heritage Site in 2014, yet the knowledge about these civilizations remains scattered across printed books, academic documents, and museum displays. This report presents the design and implementation of **PyuHeritage**, a web platform that digitally preserves and promotes the heritage of the ancient Pyu city-states.

The system is built as a full-stack web application using Node.js (Express 5) and MySQL, with server-rendered EJS views styled using Tailwind CSS. It provides a public information site covering Pyu cities, religion, language, culture, and archaeological artifacts, including interactive 3D viewing of artifacts using Google's model-viewer. An administrator dashboard enables content managers to create, update, and delete artifact records through a JSON-based CRUD API with file upload support.

The most notable feature is the **"Pyu Assistant"** — an artificial-intelligence chat application built on a Retrieval-Augmented Generation (RAG) pipeline. Questions are converted into 384-dimensional sentence embeddings locally using the all-MiniLM-L6-v2 model, and relevant context is retrieved from both indexed PDF documents and artifact records stored in the MySQL database using cosine similarity search. Answers are generated by a large language model accessed through the OpenRouter API and streamed to the browser in real time using Server-Sent Events. All answers are returned in the Myanmar (Burmese) language.

The project demonstrates how a low-cost, locally computable retrieval pipeline can be combined with a cloud-based language model to create an educational heritage assistant, and how modern web technologies can be used to preserve and share cultural knowledge for future generations.

## CHAPTER 1 — Introduction

The Pyu city-states were the earliest urban civilization to emerge in Myanmar, flourishing along the Ayeyarwady River basin for more than a thousand years before the rise of the Bagan kingdom. In 2014, the remains of their three greatest cities — Halin, Beikthano, and Sri Ksetra — were inscribed as Myanmar's first UNESCO World Heritage Site, marking them as heritage of outstanding universal value that must be preserved for future generations. Yet, despite their significance, knowledge of the Pyu civilization remains scattered across books, academic papers, and museum displays, and is largely inaccessible to the general public.

The rapid progress of artificial intelligence — in particular Retrieval-Augmented Generation (RAG) — now makes it possible to turn such scattered knowledge into an interactive experience: visitors can simply ask questions in natural language and receive grounded, source-informed answers. This chapter presents the motivation behind the PyuHeritage project, states its aim and objectives, and summarizes the advantages the system offers over traditional means of heritage education.

### 1.1 Motivation

The Pyu were a Tibeto-Burman-speaking people who flourished in the Ayeyarwady (Irrawaddy) River basin of central Myanmar from around 200 BC to AD 900, building some of the earliest urban civilizations in Southeast Asia [1]. The remains of three of their cities — **Halin**, **Beikthano**, and **Sri Ksetra** — were inscribed as Myanmar's first UNESCO World Heritage Site in June 2014 at the 38th session of the World Heritage Committee held in Doha, Qatar, under criteria (ii), (iii), and (iv) [2][3].

Despite the historical and cultural importance of these cities, information about the Pyu civilization is difficult for ordinary people, students, and tourists to access. Much of the knowledge is stored in printed academic books, research papers, and museum documentation that are not widely available online. As a result, public awareness of this "Outstanding Universal Value" heritage remains limited.

At the same time, modern artificial intelligence — particularly Retrieval-Augmented Generation (RAG) — offers a powerful way to make such knowledge interactive. A user can simply ask a question in natural language and receive an accurate, source-grounded answer. Combining this technology with a digital web archive of Pyu heritage can preserve the knowledge for future generations while making it engaging and accessible.

This project was therefore motivated by the desire to:

- **Digitally preserve** information about the ancient Pyu cities before it becomes inaccessible.
- **Raise awareness** of Myanmar's first World Heritage Site among students, researchers, and the general public.
- **Apply modern AI technology** (retrieval-augmented generation) to heritage education.
- **Explore the full software development lifecycle** by building a complete full-stack web application as a final year project.

### 1.2 Aim and Objectives

**Aim:** To design and implement a web platform that preserves, presents, and provides intelligent, AI-assisted exploration of the ancient Pyu cities' heritage.

**Objectives:**

1. To design and develop a responsive public website that presents information about the Pyu city-states, including sections on cities, religion, language, culture, and archaeological artifacts.
2. To provide interactive 3D viewing of heritage artifacts using a web-based 3D model viewer, allowing users to rotate, zoom, and inspect artifacts in augmented-reality mode.
3. To develop an administrator dashboard with full CRUD (Create, Read, Update, Delete) functionality for managing artifact records and their associated image and 3D model files.
4. To implement a retrieval-augmented generation (RAG) chat assistant, "Pyu Assistant," that answers heritage-related questions in the Myanmar language using context retrieved from indexed documents and the artifact database.
5. To store all persistent data, including artifact metadata and vector embeddings, in a structured MySQL relational database.
6. To evaluate the resulting system against its objectives and identify limitations and directions for future work.

### 1.3 Advantages of the System

The PyuHeritage system offers a number of advantages over traditional means of heritage education:

1. **Centralised digital archive** — All artifact information, descriptions, images, and 3D models are stored in a single structured database, making content easy to search, update, and maintain.
2. **Interactive 3D visualization** — Instead of static images, users can inspect artifacts as interactive 3D models, which is especially valuable for remote learners who cannot visit the physical museums.
3. **Intelligent AI assistant** — The "Pyu Assistant" chat provides instant answers to heritage questions in the Myanmar language, functioning as a 24/7 virtual guide that does not require a human expert.
4. **Grounded, source-based answers** — Because answers are generated from retrieved context (documents and database records) rather than from the model's memory alone, responses are more factual and less prone to hallucination [4].
5. **Low operational cost** — Question embedding is computed locally on the server with a small open-source model, avoiding expensive commercial embedding API calls. Only the final answer generation uses a paid cloud API.
6. **Easy content management** — Non-technical administrators can add or update artifacts through the admin dashboard without modifying code.
7. **Bilingual accessibility** — The interface is presented in the Myanmar language for local users, making national heritage accessible to the people who own it.

## CHAPTER 2 — Background Theory

### 2.1 Theoretical Foundation

#### 2.1.1 The Pyu Civilization

The Pyu city-states were early urban societies that emerged in the dry zone of the Ayeyarwady River basin. Archaeological evidence, including radiocarbon dates from intact architectural features dating back to 190 BCE, confirms more than a thousand years of continuous occupation [3]. The three inscribed cities — Halin, Beikthano, and Sri Ksetra — were walled and moated brick cities supported by sophisticated irrigation and water-management systems. Their remains include palace citadels, burial grounds, monumental brick Buddhist stupas, and inscriptions in the Pyu script [2][5].

Sri Ksetra, located near modern Pyay in Bago Region, was the largest of the three and reached its peak between the 7th and 9th centuries CE [5]. Halin, in Sagaing Region, is noted for its rectangular plan, while Beikthano, in Magway Region, exhibits an early square plan [3]. Together they represent the earliest urban civilization in Myanmar and played a key role in the spread of Buddhism and the transmission of urban-planning ideas throughout Southeast Asia [2][3].

#### 2.1.2 Retrieval-Augmented Generation (RAG)

Large pre-trained language models (LLMs) can store factual knowledge in their parameters, but they cannot easily expand or revise that memory, and they may produce plausible but incorrect "hallucinations" [4]. **Retrieval-Augmented Generation (RAG)** addresses these problems by combining a **parametric memory** (the pre-trained LLM) with a **non-parametric memory** (an external, queryable knowledge store). Given a question, the system first retrieves the most relevant passages from the external store, then conditions the LLM on those passages to generate an answer [4].

In this project, the non-parametric memory is two-fold:

- **PDF document index:** heritage and educational PDF documents are parsed, split into chunks, embedded, and stored in an in-memory vector index persisted to a JSON cache.
- **Artifact database:** every artifact record in MySQL has a corresponding embedding row, so database content can be retrieved semantically during a chat query.

This hybrid design means the assistant can answer from both unstructured documents and structured database records.

#### 2.1.3 Sentence Embeddings and Semantic Search

An **embedding** is a dense vector representation of text that captures its meaning. Semantically similar sentences map to nearby points in the vector space. **Sentence-BERT** (SBERT) introduced a siamese-network architecture that produces fixed-size sentence embeddings and allows semantic similarity to be computed efficiently with cosine similarity [6].

This project uses **`all-MiniLM-L6-v2`**, a compact sentence-transformers model based on the MiniLM architecture [7][8]. It maps sentences and short paragraphs into a **384-dimensional** dense vector space and consists of roughly 22.7 million parameters, making it small and fast enough to run locally on a CPU within the Node.js runtime via the Hugging Face Transformers library [8][9].

**Cosine similarity** measures the angle between two vectors:

```
similarity(A, B) = (A · B) / (||A|| · ||B||)
```

A score close to 1.0 means the two texts are semantically very similar. The system retrieves the top-k chunks or records whose embeddings have the highest cosine similarity to the question embedding, above a relevance threshold.

#### 2.1.4 Text Chunking and Document Processing

Long documents cannot be embedded as a single unit because the embedding model has a limited token window. The system therefore splits documents into smaller, overlapping **chunks** before embedding. The chunking strategy used in this project splits text on blank lines into segments of up to **3,000 characters** with an overlap of **200 characters**. The overlap preserves context that would otherwise be lost at chunk boundaries, improving retrieval quality.

#### 2.1.5 Web Application Architecture

The application follows the **Model-View-Controller (MVC)** design pattern:

- **Model** — MySQL queries performed through a `mysql2` connection pool (`models/`).
- **View** — Server-rendered EJS templates (`views/site/`, `views/admin/`).
- **Controller** — HTTP request handlers that call the models and render views or return JSON (`controllers/`).

The server is built on **Express 5**, a minimal and flexible Node.js web application framework [10], and runs on the **Node.js** JavaScript runtime [11]. Data is persisted in **MySQL 8**, a widely used open-source relational database management system [12].

#### 2.1.6 Server-Sent Events (SSE)

**Server-Sent Events** is a standard that allows a server to push updates over a single HTTP connection using the `text/event-stream` content type. The chat interface uses SSE to **stream** the language model's answer to the browser token-by-token, producing a natural "typing" effect and reducing perceived latency.

#### 2.1.7 3D Web Visualization

Web-based 3D visualization is performed using **model-viewer**, an open-source library from Google that renders glTF (`.glb`) 3D models in the browser without requiring a dedicated plugin [13]. It supports camera controls, auto-rotation, and AR (augmented reality) preview on compatible devices, allowing users to inspect artifacts interactively.

### 2.2 Applied Methodology

The development followed an incremental, prototype-oriented methodology. The project evolved through several stages — from a static content site, to a dynamic artifact catalog with a 3D page, to the final integration of the RAG-based chat assistant — as reflected in the project's version history.

#### 2.2.1 RAG Pipeline

The applied RAG pipeline consists of the following stages:

1. **Document ingestion (indexing):** On server startup, PDF files in `rag/documents/` are parsed with the `pdf-parse` library. The extracted text is split into overlapping chunks by the chunker module (`rag/chunker.js`).
2. **Embedding:** Each chunk is encoded into a 384-dimensional vector using `all-MiniLM-L6-v2` through the embedding module (`rag/embedder.js`). Embeddings are computed in batches and cached in `rag/cache.json` to make subsequent starts fast.
3. **Vector storage:** Chunks and their embeddings are stored in an in-memory vector store (`rag/vectorStore.js`) that persists to the JSON cache.
4. **Artifact store:** On startup, the artifact store (`rag/artifactStore.js`) loads every row of the `artifact_embeddings` table from MySQL into memory, keeping document and artifact retrieval in the same framework.
5. **Query handling:** When a user submits a question:
   - The question is embedded with the same model.
   - Cosine similarity search retrieves the top-5 PDF chunks and the top-5 artifact records, filtered to a relevance threshold of 0.3.
   - The retrieved text is assembled into a context prompt in a "hybrid context" builder (`rag/index.js`).
   - A system prompt instructs the model to answer in Myanmar and to ground answers in the provided context.
   - The context and question are sent to the OpenRouter LLM API (by default the `deepseek/deepseek-v4-flash` model).
   - The answer is returned either as plain JSON or streamed to the browser over SSE.
6. **Embedding synchronization:** Whenever an administrator creates, updates, or deletes an artifact through the admin API, the artifact store automatically upserts or removes the corresponding embedding row in MySQL, keeping the chat's knowledge up to date.

- **3D artifacts:** `image` + `model` fields; the model must be a `.glb` file (binary glTF); maximum file size 100 MB.

All persistent application data is stored in a **MySQL** database named `pyu`. The schema is created by the SQL scripts in `node/database/`.

#### 3.2.2 Table Schemas

**`artifacts`** — stores regular artifact records:

```sql
CREATE TABLE artifacts (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    title       VARCHAR(255) NOT NULL,
    description TEXT NOT NULL,
    image_url   VARCHAR(500) DEFAULT NULL,
    category    VARCHAR(100) DEFAULT 'General',
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

**`three_d_artifacts`** — stores artifact records that include a 3D model:

```sql
CREATE TABLE three_d_artifacts (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    title       VARCHAR(255) NOT NULL,
    description TEXT         NOT NULL,
    image_url   VARCHAR(500) DEFAULT NULL,
    model_url   VARCHAR(500) DEFAULT NULL,
    category    VARCHAR(100) DEFAULT 'General',
    created_at  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

**`artifact_embeddings`** — stores the 384-dimensional vector embeddings that power semantic retrieval in the chat. Each row is uniquely keyed by `(source_table, source_id)`, so every artifact in the two catalog tables has exactly one embedding row:

```sql
CREATE TABLE artifact_embeddings (
    id           INT AUTO_INCREMENT PRIMARY KEY,
    source_table VARCHAR(50)  NOT NULL,
    source_id    INT          NOT NULL,
    title        VARCHAR(255) NOT NULL,
    description  TEXT,
    category     VARCHAR(100),
    embedding    TEXT         NOT NULL,
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uq_source (source_table, source_id)
);
```

#### 3.2.3 File Storage

Media files (artifact images and `.glb` 3D models) are stored on the server file system under `uploads/`, with their URLs (e.g. `/uploads/artifact-1234567890.jpg`) referenced by the `image_url` and `model_url` columns. Stale files are deleted from disk when a record is updated or removed. The document chunks used by the chat are additionally cached in `rag/cache.json` for fast startup.

#### 3.2.4 Data Flow During a Chat Query

1. User submits a question via `POST /chat`.
2. The question is embedded with `all-MiniLM-L6-v2`.
3. The vector store returns the top-5 PDF chunks; the artifact store returns the top-5 database records (both filtered by a cosine-similarity threshold of 0.3).
4. Retrieved text is assembled into a context prompt.
5. The prompt is sent to the OpenRouter API for answer generation.
6. The answer is streamed to the browser via SSE.

#### 4.1.1 Home Page (`/`)

The home page presents a full-screen hero slider featuring the three Pyu cities, a headline describing the Pyu civilization, and two call-to-action buttons ("City-states" and "Ask about Pyu"). Below the hero, a grid of cards introduces **Halin**, **Beikthano**, and **Sri Ksetra**, each with an image, a short description, and a "read more" link. - **Zoom** in and out.

- Launch an **augmented-reality (AR)** preview on compatible devices.
- Close the viewer with the close button or the **Esc** key.

#### 4.1.5 Pyu Assistant Chat (`/chat`)

The chat page shows a "Pyu Assistant" conversation panel with a suggestion-chip area offering example questions such as "Tell me about Halin", "Explain the Pyu city-states", and "Tell me about Pyu culture".

To ask a question:

1. Type a question in the input field (or click a suggestion chip).
2. Press the send button. A "please wait" typing indicator appears.
3. The answer is **streamed token by token** into a message bubble, in the Myanmar language.
4. The assistant grounds its answers in the retrieved document and artifact context, so answers about the Pyu cities and artifacts are informed by the indexed sources.

#### 4.1.6 Admin Dashboard (`/admin/dashboard`)

The admin dashboard provides content managers with a full CRUD interface for artifacts and 3D artifacts:

- **Add an artifact:** enter a title, description, and category, and upload an image.
- **Add a 3D artifact:** additionally upload a `.glb` 3D model.
- **Edit:** update any field and optionally replace the image or model.
- **Delete:** remove a record; the associated embedding and media files are cleaned up automatically.

Because the admin API is JSON-based, content can also be managed programmatically using the routes listed in section 3.1.2.

## CHAPTER 5 — Conclusion

### 5.1 Conclusion

This project set out to design and build a web platform that preserves, presents, and provides intelligent, AI-assisted exploration of the ancient Pyu cities of Myanmar. All of the stated objectives were successfully achieved:

- A **responsive public website** was implemented with pages covering the Pyu city-states, religion, language, culture, and archaeological artifacts, styled with Tailwind CSS and supporting both light and dark themes.
- **Interactive 3D viewing** of heritage artifacts was provided through Google's model-viewer, letting users rotate, zoom, and view artifacts in augmented-reality mode.
- An **administrator dashboard** with a full JSON-based CRUD API enables content managers to create, update, and delete artifact records (including image and `.glb` model uploads) without touching code.
- A **retrieval-augmented generation chat assistant**, "Pyu Assistant," answers heritage questions in the Myanmar language, grounding its answers in context retrieved from indexed PDF documents and the artifact database.
- All persistent data, including metadata and vector embeddings, is stored in a structured **MySQL** database.
- The system was evaluated against its objectives, and its limitations and future directions are identified below.

From a technical perspective, the project provided invaluable hands-on experience in full-stack JavaScript development (Express, EJS, MySQL), in applying modern natural-language-processing techniques such as sentence embeddings, cosine similarity, and RAG, and in integrating third-party AI services through REST and streaming APIs. It also highlighted the practical engineering concerns of such systems — model download and caching, embedding synchronization with a database, prompt design, and graceful handling of missing API keys.

On a broader level, the project demonstrates that heritage preservation does not require expensive or complex infrastructure. A modest web server, a free open-source embedding model, and a cloud LLM are sufficient to build an educational, interactive, and source-grounded assistant for cultural heritage. PyuHeritage is a small but meaningful contribution to making Myanmar's first World Heritage Site accessible, engaging, and preserved for future generations.

### 5.2 Limitation

Although the system functions as intended, several limitations were identified:

1. **English-centric embedding model** — The `all-MiniLM-L6-v2` model is trained primarily on English text. Because the PyuAssistant answers in Myanmar, semantic retrieval quality for Burmese queries is limited. A multilingual embedding model (for example a Burmese-supporting sentence-transformer) would improve retrieval accuracy.
2. **Document corpus mismatch** — The PDF documents currently shipped in `rag/documents/` are English natural-language-processing lecture notes rather than heritage-specific texts. The chat therefore answers heritage questions mainly from the artifact database, and its knowledge depth depends on the documents actually provided.
3. **Internet dependency** — Answer generation requires an active internet connection and a valid OpenRouter API key. Without connectivity, the chat cannot produce answers. The first server start is also slow because the embedding model (about 90 MB) must be downloaded once.
4. **No authentication or authorization** — The admin dashboard and CRUD API have no login or role-based access control. Anyone who reaches the admin routes can modify or delete content. A simple authentication layer would be needed for production deployment.
5. **No user session or conversation memory** — The chat is stateless; it does not remember previous questions in a conversation, so follow-up questions are answered without context.
6. **In-memory vector index** — The PDF chunk index is rebuilt from the JSON cache in memory and is not a dedicated vector database; for very large document collections, a specialized vector store would scale better.
7. **No automated tests or CI** — The project has no unit, integration, or end-to-end tests and no continuous-integration pipeline, which increases the risk of regressions during future changes.

### Future Work

Possible directions for future development include:

- Replacing the embedding model with a **multilingual/Burmese-capable model** and evaluating retrieval quality on Burmese queries.
- Adding **conversation memory** so the assistant can handle multi-turn dialogues.
- Introducing **user authentication** and **role-based access control** for the admin module.
- Adding **automated tests** and a **CI/CD pipeline**.
- Expanding the heritage document corpus and adding a **document upload** feature for administrators.
- Migrating to a dedicated **vector database** (for example a MySQL `VECTOR` type or an external ANN index) for better scalability.
